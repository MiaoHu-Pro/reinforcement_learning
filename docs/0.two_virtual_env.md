# The two Python virtual environments

This project has two separate Python virtual environments because it contains
both current Gymnasium examples and archived Gym examples.

```text
reinforcement_learning/
├── .venv/                 # Current code: Gymnasium, managed by uv
└── old_version_rf_env/    # Archived code: Gym 0.25.2, managed by venv + pip
```

The environments are intentionally isolated. Installing or removing a package
in one environment does not change the other environment.

## Quick reference

| Environment | Purpose | Environment manager | Package manager | Main API |
|---|---|---|---|---|
| `.venv` | Current examples such as `code-1.py` and `code-2.py` | `uv` | `uv` | Gymnasium |
| `old_version_rf_env` | Archived examples such as `code-1-old.py` | `python3.12 -m venv` | `pip` | Gym 0.25.2 |

## 1. The current `.venv` environment

`.venv` is the main project environment. It is managed by `uv` using:

- `pyproject.toml`, which declares the project dependencies;
- `uv.lock`, which records the resolved dependency versions;
- `.python-version`, which records the selected Python version.

The current source files use Gymnasium:

```python
import gymnasium as gym
```

They use the current reset and step APIs:

```python
state, info = env.reset()

next_state, reward, terminated, truncated, info = env.step(action)
done = terminated or truncated
```

### Run current code

From the project root:

```bash
uv run python demo/day02/code-1.py
uv run python demo/day02/code-2.py
```

It is also possible to invoke its interpreter explicitly:

```bash
.venv/bin/python demo/day02/code-1.py
```

### Add or synchronize current dependencies

Use `uv` for `.venv`:

```bash
uv add PACKAGE_NAME
uv sync
```

Do not install legacy Gym into `.venv`. Its dependencies are defined for the
current Gymnasium-based project.

## 2. The legacy `old_version_rf_env` environment

`old_version_rf_env` exists only for running archived examples that import the
unmaintained `gym` package:

```python
import gym
```

It was created independently with standard Python `venv`:

```bash
python3.12 -m venv old_version_rf_env
```

It is **not managed by `uv`**. Its packages are installed using the Python and
`pip` executables inside `old_version_rf_env`:

```bash
old_version_rf_env/bin/python -m pip install \
    "gym==0.25.2" \
    "numpy==1.26.0" \
    matplotlib \
    "pygame>=2.6.1" \
    torch
```

`pygame` is required by Gym's classic-control environments when code calls
`env.render(...)`. Without it, `code-2-old.py` can train but fails when it tries
to render the final CartPole trajectory.

The environment currently contains the main versions needed by
`code-1-old.py`:

```text
Python      3.12.13
Gym         0.25.2
NumPy       1.26.0
PyTorch     2.13.0
Matplotlib  3.11.1
Pygame      2.6.1
```

### Run archived code without activation

Using the interpreter explicitly is the clearest option:

```bash
old_version_rf_env/bin/python demo/day02/code-1-old.py
```

This guarantees that the legacy interpreter is used, regardless of which shell
environment is currently active.

### Activate the legacy environment

Alternatively:

```bash
source old_version_rf_env/bin/activate
python demo/day02/code-1-old.py
deactivate
```

After activation, the shell prompt may show:

```text
(old_version_rf_env)
```

### Install another legacy dependency

When the environment is not activated:

```bash
old_version_rf_env/bin/python -m pip install PACKAGE_NAME
```

When it is activated:

```bash
python -m pip install PACKAGE_NAME
```

Do not use `uv add` or `uv sync` for `old_version_rf_env`; those commands manage
the main project environment and its lock file.

## Checking which environment is being used

Before installing packages or running a script, check the interpreter:

```bash
python -c "import sys; print(sys.executable)"
```

When the main environment is active, the result should end with:

```text
/reinforcement_learning/.venv/bin/python
```

When the legacy environment is active, it should end with:

```text
/reinforcement_learning/old_version_rf_env/bin/python
```

You can also inspect package versions:

```bash
python -c "import gym; print(gym.__version__)"
```

or, for the current environment:

```bash
.venv/bin/python -c "import gymnasium; print(gymnasium.__version__)"
```

## Which environment should run each file?

```text
demo/day02/code-1.py      → .venv
demo/day02/code-2.py      → .venv
demo/day02/code-1-old.py  → old_version_rf_env
demo/day02/code-2-old.py  → old_version_rf_env
```

The same naming convention applies to other archived files ending in
`-old.py` when they import `gym` rather than `gymnasium`.

## Expected warnings from the legacy environment

Running old Gym code prints messages such as:

```text
Gym has been unmaintained since 2022...
CartPole-v0 is out of date...
```

These warnings are expected. The legacy environment isolates old dependencies,
but it does not make the old Gym API current or maintained.

Use `.venv` and Gymnasium for new development. Use `old_version_rf_env` only
when studying or comparing the archived implementations.

## Git handling

Virtual environments contain generated files and installed third-party
packages, so they should not be committed to Git. The legacy environment is
excluded in `.gitignore`:

```gitignore
old_version_rf_env/
```

The main `.venv` should also remain untracked. If it is not already covered by
a global Git ignore rule, add:

```gitignore
.venv/
```

The source files, `pyproject.toml`, and `uv.lock` should be tracked; the virtual
environment directories themselves should not.

## Summary

```text
Current code:
    uv run python FILE.py
    → uses .venv
    → uses Gymnasium

Archived code:
    old_version_rf_env/bin/python FILE-old.py
    → uses old_version_rf_env
    → uses Gym 0.25.2
```

The central rule is: **use `uv` only for `.venv`, and use the legacy
environment's own `python -m pip` for `old_version_rf_env`.**
