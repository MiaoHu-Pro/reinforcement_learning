# Understanding trajectory collection and policy updates in `code-2-reinforce-policy-gradient-vectorized.py`

This note explains the training workflow in
[`../rl_learning_demo/day02/code-2-reinforce-policy-gradient-vectorized.py`](../rl_learning_demo/day02/code-2-reinforce-policy-gradient-vectorized.py). The program implements the
Monte Carlo REINFORCE policy-gradient algorithm for CartPole.

The most important timing rule is:

> One complete trajectory is collected with fixed policy weights. After the
> episode finishes, `backward()` computes gradients and `optimizer.step()`
> updates the weights once.

## High-level workflow

For every training episode, `train_agent()` performs these two calls:

```python
trajectory = agent.collect_trajectory(env, seed=episode_seed)
loss = agent.update(trajectory)
```

The complete flow is:

```text
Current weights θ_k
       │
       ▼
Collect one complete episode
(weights do not change)
       │
       ▼
states, actions, rewards
       │
       ▼
Calculate G_t for every time step
       │
       ▼
Run the stored states through the policy again
and construct the REINFORCE loss
       │
       ▼
zero_grad() → backward() → optimizer.step()
       │
       ▼
New weights θ_(k+1)
       │
       ▼
Collect the next episode
```

There are 3,000 episodes by default, so normally there are 3,000 policy
updates—one update after each episode.

## Phase 1: collect a trajectory

### What does one trajectory contain?

In this program, **one complete trajectory contains the experience from step 0
to the final step of one episode**:

```text
τ = (S_0, A_0, R_0, S_1, A_1, R_1, ..., S_(T-1), A_(T-1), R_(T-1), S_T)
```

Here, `T` is the point where the episode is terminated or truncated. Therefore,
a trajectory does not normally contain experiences from multiple episodes.

While the episode is still running, the lists hold only a **partial
trajectory**, from step 0 to the current step. For example:

```text
After step 0: (S_0, A_0, R_0, S_1)
After step 1: (S_0, A_0, R_0, S_1, A_1, R_1, S_2)
...
At episode end: the complete trajectory from step 0 to the final step
```

`collect_trajectory()` does not return the partial trajectory at every step. It
waits until the `while` loop finishes and returns one complete trajectory for
the episode. That complete trajectory is then passed to `update()`.

The training loop calls `collect_trajectory()` once per episode. Consequently:

- one episode produces one complete trajectory;
- one trajectory produces one policy update;
- 3,000 episodes produce 3,000 trajectories and 3,000 updates by default;
- after an update, the old trajectory is no longer used and the next episode
  collects a new trajectory using the updated policy.

```text
Episode 1 → trajectory τ_1 → update weights
Episode 2 → trajectory τ_2 → update weights
Episode 3 → trajectory τ_3 → update weights
...
```

### One realized trajectory versus many possible trajectories

The stochastic policy can produce many **possible** trajectories. Even from a
similar initial state, sampling different actions can lead to different paths:

```text
Possible τ_1: left  → left  → right → ...
Possible τ_2: right → left  → right → ...
Possible τ_3: right → right → left  → ...
```

One execution of an episode realizes only one of those possible paths. The code
collects that one realized path as the episode's trajectory:

```text
Distribution of all possible trajectories under policy π
                         │
                         │ run one episode
                         ▼
              sample one trajectory τ
```

Therefore, an episode does **not** collect several trajectories and then select
one of them. It interacts with the environment once, step by step, producing
one trajectory as the episode unfolds:

```text
1 episode = 1 realized trajectory = 1 policy update
```

Other policy-gradient implementations may collect a batch of complete
trajectories before performing one update:

```text
Episode 1 → τ_1 ┐
Episode 2 → τ_2 ├─ one batch update
Episode 3 → τ_3 ┘
```

That is not the workflow in `code-2-reinforce-policy-gradient-vectorized.py`. Here, the policy is updated immediately
after each single completed trajectory, before the next episode begins.

The trajectory is collected by `Agent.collect_trajectory()`:

```python
state, _ = env.reset(seed=seed)
states = []
actions = []
rewards = []

terminated = truncated = False
while not (terminated or truncated):
    action = self.get_action(state)
    next_state, reward, terminated, truncated, _ = env.step(action)

    states.append(state)
    actions.append(action)
    rewards.append(float(reward))
    state = next_state
```

At time step `t`, the following transition occurs:

```text
S_t ──policy──► A_t ──environment──► R_t, S_(t+1)
```

The method saves:

- `states[t]` = the state `S_t` before taking the action
- `actions[t]` = the sampled action `A_t`
- `rewards[t]` = the reward `R_t` received after that action

For an episode containing `T` steps, the returned trajectory is:

```python
trajectory = (states, actions, rewards)
```

with:

```text
states  = [S_0, S_1, ..., S_(T-1)]
actions = [A_0, A_1, ..., A_(T-1)]
rewards = [R_0, R_1, ..., R_(T-1)]
```

### Are weights updated during collection?

No. `get_action()` contains:

```python
with torch.no_grad():
    logits = self.policy(state_tensor).squeeze(0)
```

`torch.no_grad()` tells PyTorch not to construct an automatic-differentiation
graph while choosing actions. The policy is only being used to collect data at
this point.

Therefore, during the whole episode:

- the policy uses the same weights `θ_k`;
- no gradients are calculated;
- `backward()` is not called;
- `optimizer.step()` is not called;
- the environment interaction itself is not differentiated.

The action is sampled from the current policy:

```python
Categorical(logits=logits).sample()
```

This sampling operation is not differentiable, but that is expected. REINFORCE
does not differentiate through the sampled action or through the environment.
It later differentiates the log-probability of the action that was sampled.

## Phase 2: calculate the return for every step

Once the episode finishes, `Agent.update()` receives the complete trajectory:

```python
states, actions, rewards = trajectory
returns = self.discounted_returns(rewards)
```

For every time step, the discounted return is:

```math
G_t = R_t + \gamma R_{t+1} + \gamma^2 R_{t+2} + \cdots
```

It can be calculated backward using:

```math
G_t = R_t + \gamma G_{t+1}
```

That is what `discounted_returns()` does:

```python
returns = []
return_from_t = 0.0

for reward in reversed(rewards):
    return_from_t = reward + self.gamma * return_from_t
    returns.append(return_from_t)

returns.reverse()
```

For example, suppose:

```python
rewards = [1.0, 1.0, 1.0]
gamma = 0.9
```

The backward calculation is:

```text
G_2 = 1 + 0.9 × 0   = 1.00
G_1 = 1 + 0.9 × 1   = 1.90
G_0 = 1 + 0.9 × 1.9 = 2.71
```

After reversing the result back into time order:

```python
returns = [2.71, 1.90, 1.00]
```

Each action receives its own return:

```text
A_0 is weighted by G_0
A_1 is weighted by G_1
A_2 is weighted by G_2
```

The returns are data, not model outputs, so their tensors do not require
gradients.

## Phase 3: run a differentiable policy forward pass

During collection, the policy forward pass used `torch.no_grad()`. Consequently,
`update()` must run the stored states through the policy again:

```python
distribution = Categorical(logits=self.policy(state_tensor))
selected_log_probabilities = distribution.log_prob(action_tensor)
```

This time there is no `torch.no_grad()`, so PyTorch builds a computation graph:

```text
policy weights θ
      │
      ▼
linear layers → logits → log π_θ(A_t | S_t) → loss
```

Recomputing the probabilities is valid because the weights have not changed
since the trajectory was collected. The trajectory is therefore **on-policy**.

### Tensor shapes

For an episode with `T` steps:

| Value | Shape | Meaning |
|---|---:|---|
| `state_tensor` | `[T, 4]` | all CartPole states |
| policy logits | `[T, 2]` | scores for left and right |
| `action_tensor` | `[T]` | action selected at every step |
| `selected_log_probabilities` | `[T]` | `log π(A_t|S_t)` |
| `returns` | `[T]` | one `G_t` per step |
| `loss` | scalar | one loss for the episode |

### Where is `gather()`?

The current code uses:

```python
selected_log_probabilities = distribution.log_prob(action_tensor)
```

This selects the log-probability of the action taken at each time step. Its
`gather()` equivalent is:

```python
all_log_probabilities = F.log_softmax(self.policy(state_tensor), dim=1)
selected_log_probabilities = all_log_probabilities.gather(
    dim=1,
    index=action_tensor.unsqueeze(1),
).squeeze(1)
```

Both versions produce the same `[T]` result. `Categorical.log_prob()` expresses
the policy-gradient operation more directly and handles the log-probability
calculation in a numerically stable way.

## Phase 4: construct the REINFORCE loss

The theoretical objective is to increase:

```math
J(\theta) = \mathbb{E}\left[\sum_t G_t \log \pi_\theta(A_t|S_t)\right]
```

PyTorch optimizers minimize losses, so the code adds a minus sign:

```python
loss = -(selected_log_probabilities * returns).mean()
```

For one three-step episode, this means:

```math
L = -\frac{1}{3}\left[
G_0\log\pi_\theta(A_0|S_0) +
G_1\log\pi_\theta(A_1|S_1) +
G_2\log\pi_\theta(A_2|S_2)
\right]
```

If an action leads to a large positive return, minimizing this loss tends to
increase that action's probability in the corresponding state. Actions with
smaller returns receive weaker reinforcement.

The call to `.mean()` does not change which direction the gradient points. It
scales the loss by the number of episode steps so episodes of different lengths
produce more comparable gradient magnitudes.

## Phase 5: clear gradients, backpropagate, and update

The actual training operation is:

```python
self.optimizer.zero_grad()
loss.backward()
self.optimizer.step()
```

These three statements do different jobs.

### 1. `optimizer.zero_grad()`

PyTorch accumulates gradients by default. This call clears gradients left from
the previous episode:

```python
self.optimizer.zero_grad()
```

Without it, the new gradients would be added to the old ones, mixing multiple
episode updates unintentionally.

### 2. `loss.backward()`

This performs backpropagation through the computation graph created by the
forward pass:

```python
loss.backward()
```

It calculates:

```math
\frac{\partial L}{\partial \theta}
```

for every trainable parameter and stores the results in each parameter's
`.grad` attribute.

Crucially, `backward()` **calculates gradients but does not change the weights**.

### 3. `optimizer.step()`

Adam reads the gradients stored in `.grad` and changes the policy weights:

```python
self.optimizer.step()
```

Conceptually:

```math
\theta_{k+1} = \theta_k - \alpha \cdot \text{AdamUpdate}(\nabla_\theta L)
```

This is the exact point where the policy network's weights are updated.

The next episode is then collected using the new weights `θ_(k+1)`.

## Timeline of one episode

```text
1. Start with weights θ_k
2. reset() the environment
3. sample A_0, execute it, store S_0/A_0/R_0
4. sample A_1, execute it, store S_1/A_1/R_1
5. continue until terminated or truncated
6. calculate G_0, G_1, ..., G_(T-1)
7. recompute log π_θ(A_t|S_t) with gradient tracking enabled
8. construct one scalar episode loss
9. zero_grad() clears gradients from episode k-1
10. backward() calculates gradients for episode k
11. step() changes θ_k into θ_(k+1)
12. begin the next episode with θ_(k+1)
```

## What happens during testing?

`test_agent()` runs only after all training episodes. It calls:

```python
action = agent.get_action(state, greedy=True)
```

The greedy action is the action with the largest policy score. Because
`get_action()` uses `torch.no_grad()` and the test function never calls
`backward()` or `optimizer.step()`, testing does not modify the trained weights.

## Is a value function used here?

No. This file implements plain Monte Carlo REINFORCE:

- `G_t` is a sampled discounted return from one trajectory;
- the policy network estimates action probabilities;
- there is no separate network estimating `V(S_t)`;
- there is no learned baseline in this example.

A value-function baseline would typically replace the raw weight `G_t` with an
advantage estimate such as:

```math
A_t = G_t - V(S_t)
```

That can reduce gradient variance, but it is a later extension of the workflow
shown here.

## Short summary

| Operation | During collection? | During `update()`? | Changes weights? |
|---|:---:|:---:|:---:|
| Policy forward pass | Yes, with `no_grad()` | Yes, with gradient tracking | No |
| Environment `step()` | Yes | No | No |
| Calculate `G_t` | No | Yes | No |
| Construct loss | No | Yes | No |
| `zero_grad()` | No | Yes | No |
| `backward()` | No | Yes | No; calculates gradients |
| `optimizer.step()` | No | Yes | **Yes** |

In one sentence: **collect a complete episode without changing the policy,
calculate a loss from that episode, backpropagate once, update once, and then
repeat with the new policy.**
